# AGENTS.md

## What it is
Real-time noise filter for ham radio SSB voice on Windows. It captures live audio from a standard Windows audio device (WASAPI endpoint), removes white noise, and plays the result to a standard Windows audio device. While the radio is keyed (PTT state polled from one of three user-selectable sources: a rigctld server such as WSJT-X's rigctld-wsjtx.exe, the classic OmniRig's COM interface, or the radio's CAT port directly) the denoiser is bypassed and the raw band-passed signal passes through.

## Stack
- Rust (rustup `stable`), builds a single Windows `.exe`. The session runs on a Linux OpenCode server: `cargo check`/`test`/`clippy` run natively (host gcc compiles the C++ engine), and the exe is cross-compiled — `cargo build --release --target i686-pc-windows-gnu` (binary in `target/i686-pc-windows-gnu/release/`, needs mingw-w64 g++ for the `cc` crate). **The release build is 32-bit** because the OmniRig PTT method requires it (see the activation caveat); the app itself is bitness-neutral, and `x86_64-pc-windows-gnu` still builds here for comparison. Both targets import only system DLLs — no `libstdc++-6.dll`, no `libgcc_s_*.dll`. The C++ stdlib is static-linked via `cpp_link_stdlib_static(true)` in `build.rs` (GNU branch): cc's default emits `rustc-link-lib=stdc++` (dylib kind), which rustc wraps in `-Wl,-Bdynamic` — a per-library flag that overrides any global `-static`, so the exe would otherwise import `libstdc++-6.dll`, absent on the user's stock Windows machine; the static-kind emit keeps the app a single self-contained .exe. The original toolchain was `x86_64-pc-windows-msvc` on Windows
- Fast feedback: `cargo check`; lint: `cargo clippy`; tests: `cargo test`
- `cpal 0.18` for audio I/O (WASAPI backend), `egui`/`eframe 0.36` for the GUI — deliberately the `glow` (OpenGL) renderer instead of eframe's default `wgpu` (Vulkan): some Intel Vulkan drivers crash at startup on other people's machines
- Noise reduction: `nnnoiseless 0.5.2` (pure-Rust port of Xiph's RNNoise, BSD-3); with `default-features = false` its only deps are `easyfft` + `once_cell` (both transitive); GUI-selectable second engine: vendored C++20 `SpectralNR` (AetherSDR's EMNR port, GPL-3.0) compiled with `cc` behind an `extern "C"` bridge (`src/nr2.rs`)
- Pre-filter: homegrown 2nd-order biquad bandpass (HP 300 Hz + LP 3 kHz, RBJ cookbook coefficients, direct form II transposed) in `src/biquad.rs`
- Output rate: homegrown streaming linear-interpolation resampler (`src/resampler.rs`), used on the render path when the output device's mix rate is not 48 kHz
- Rig PTT: one background poller thread (`src/ptt.rs`) serving three user-selectable sources — a homegrown minimal rigctld TCP client (std-only), the classic OmniRig COM interface (hand-rolled Win32 FFI, `src/omnirig.rs`, no crate), and direct CAT polling of the radio (58 per-model status probes, `src/radio.rs`) via `serialport 4` (MPL-2.0, GPL-3.0-compatible; `default-features = false` drops the Linux-only libudev dep; pure FFI on Windows — no new DLLs)
- Settings: homegrown std-only `key=value` file at `%APPDATA%\SSB Noise Filter\config.ini` (`src/settings.rs`), remembers the PTT method and its parameters plus the connection state (no serde)

## Decided: noise reduction approach
- RNNoise (recurrent neural net, 48 kHz, 480-sample = 10 ms frames) via `nnnoiseless`, low-level `DenoiseState` API; the RNN state lives directly in the capture callback
- Samples are f32 but must be in the i16 PCM range `[-32768, 32767]` (not `[-1, 1]`): the capture loop scales by 32768 around `process_frame` and scales the blended frame back after
- RNNoise's first frame is discarded (its fade-in artifact) — 10 ms of silence at startup
- SSB voice is 300–3000 Hz, so the mic signal is bandpassed *before* the denoiser (avoids out-of-band "underwater" artifacts)
- The denoised output is blended with the band-passed original **in the time domain, one whole-signal coefficient** (`wet·denoised + (1−wet)·raw`), scaled by the GUI "Noise reduction" slider (default 80%, 100% = full RNNoise, 0% = pure band-pass through). The raw feed (speaker → mic, band-passed) is itself the muffled "underwater" sound, so the slider is the direct control on how much of it gets through: at high settings the voice is entirely the RNN's output. RNNoise's per-band gains attack instantly (only release is smoothed), so on flickering weak SSB signals the gain snaps cause pops and untrusted speech gets crushed; the `(1−wet)` raw floor damps those snaps and keeps a floor under weak signals
- The *input* must be 48 kHz / 32-bit float (WASAPI shared mode + RNNoise); the *output* may run at any mix rate — the render callback linearly resamples 48 kHz to the device rate (safe because the signal is band-limited to 3 kHz)
- Output volume: a 0–300% slider (default 100%) applies a plain gain in the render callback to the samples right before they are written to the output device (after the resampler, where present), so the "Out" meter shows the post-gain level the speakers actually receive; above 100% the gain exceeds unity, so the post-gain samples are clamped to ±1.0 (WASAPI's float range) and loud peaks simply clip
- Rejected: WebRTC NS (less proven on SSB), spectral subtraction (musical noise), **per-band spectral blend with noise-floor gating** (built at `e276dce`, reverted): it was meant to keep the raw timbre in active bands, but the raw feed *is* the underwater sound, and the activity cap left ≥50% raw in the voice bands at *every* slider position, so the muffle could not be removed at any setting; the uniform blend gives the user a direct muffle-vs-static trade; **crush-aware wet easing** (prototyped and reverted): a detector that eased the wet down while the RNN strongly attenuated a signal above the noise floor sounded robotic/buzzy on loud speech and let static through at 100% — the RNN's per-frame gain wobbles at syllable rate even on confident speech, and any per-frame-varying wet between the two phase-different signals is a moving comb (the per-band trap all over again), while white noise constantly exceeds its own average floor, so the detector fired on static; the tension is fundamental: fast enough to rescue a syllable = buzzy, smooth enough = too slow

## Decided: second filter — NR2 (EMNR)
- The app is licensed **GPL-3.0** (LICENSE at the repo root) to accommodate the NR2 engine; the GitHub repo stays **private for now**
- The engine is the C++20 port of the original EMNR (emnr.c, Warren Pratt NR0V, TAPR OpenHPSDR WDSP) that AetherSDR ships (`SpectralNR`, GPL-3.0), vendored in `third_party/spectralnr/`. The original emnr.c hard-requires FFTW3, so we use the port: its FFTW path is fully `#ifdef HAVE_FFTW3` (undefined here) with a built-in radix-2 FFT fallback — **no FFTW**
- Compiled with the `cc` crate (MSVC, C++20) behind a small `extern "C"` bridge (`nr2_bridge.cpp`): MSVC's C++ name mangling differs from Rust's `extern "C++"`, so a C bridge is required
- The port's Qt usage was limited to the one-time gamma-table startup decode (base64/zlib/SHA-256) and two AetherSDR includes; that decode has been de-Qt'ed (pre-decoded table + std checks), with a Rust test pinning the table's integrity against the upstream SHA-256
- The gamma-table accessors are public statics (`gammaTablesValid()`, `gammaTableValue(i)`) exposed through the bridge without a handle; the OLA read's `Q_ASSERT` was replaced with a comment (debug-only Qt check — during the ~2-hop OLA startup ramp the ring legitimately holds zeros: the expected startup silence, matching upstream release builds)
- Runs at 48 kHz — the port is rate-independent (all constants hop-scaled, band edges in Hz, gain lookup is a (γ, ξ) grid); geometry fft 512 / overlap 2 reproduces AetherSDR's 24 kHz/256 operating point at double rate. Streaming mono f32 `process(in, out, n)`; parameters are `std::atomic`
- GUI "Filter" dropdown selects RNNoise | NR2; the choice persists to config.ini (`filter=0|1`) and is restored at startup. **Both engines are fed every sample** (stays warm, instant switching), selected per block via `Arc<AtomicU8>`; the NR slider keeps its wet/dry meaning in both modes. The two paths run on different block boundaries in one capture callback — RNNoise 480-sample frames, NR2 exactly 256-sample calls at the hop cadence (its overlap-add corrupts at any other cadence) — each with its own consumed index into the band-passed input buffer; only the selected engine's blended block reaches the ring, the first pushed block is discarded (NR2's ~2-hop OLA startup ramp + ~1 s dry→wet ramp, mirroring RNNoise's first-frame discard), and a switch fills the boundary gap with silence (≤ one new-engine block + two old-engine blocks, worst case ~25 ms switching away from RNNoise) so the timeline stays continuous. The NR2 blend's raw side is delayed by `nr2::DELAY` (one FFT frame, ~10.7 ms) to match the engine's built-in OLA delay — but while keyed the path pushes the *current* raw with no delay, so the TX monitor has the same latency as RNNoise. On the TX→RX PTT edge NR2's `resetTransient()` is called (AetherSDR's own pattern: discards the stale overlap-add ring, keeps the converged noise estimate, re-arms the ramp)

## Decided: PTT detection — three selectable methods
- One background poller thread (`src/ptt.rs`, replacing the old `src/rigctl.rs`) serves whichever of the three sources the GUI "PTT method" dropdown selects: `rigctld (TCP)` | `OmniRig` | `COM port`. The three are mutually exclusive — each owns the path to the rig (the TCP link, OmniRig's port handle, or the port itself) — and switching method while connected auto-disconnects. The target is `{nonce, source}`: every Connect bumps the nonce, so even an identical re-select forces a fresh connection; no target = disconnected. Poll cadence 100 ms, reconnect cadence 1 s
- **rigctld** (unchanged behavior): TCP to a rigctld server ("default" protocol: no banner, no ACK); the short command `t\n` answers a bare PTT state `0` RX / `1` TX / `2` TX mic / `3` TX data, or `RPRT <n>` when the rig errors (keeps the last state). A dead link (timeout/close/malformed line) drops the connection; state `DISCONNECTED` (255) means no live source
- **OmniRig** (`src/omnirig.rs`): the classic freeware COM object (VE3NEA, dxatlas.com) that owns the radio's serial port and shares it via COM. The poller thread does `CoInitializeEx` (MTA; idempotent) → `GetActiveObject(CLSID_OmniRigX)` → `CoCreateInstance(CLSCTX_LOCAL_SERVER)` fallback → the selected rig slot → polls the `Tx` property (`PM_RX`/`PM_TX`). The type library exposes exactly two rig slots: `Get_Rig1` = slot 9, `Get_Rig2` = slot 10; the GUI picks between them. Hand-rolled Win32 FFI, no crate, links `ole32` (plus `advapi32` for the install check): vtable slots are read through one `slot_bits` helper (first pointer-sized word = vtable pointer; entries are pointer-sized — the helper is bitness-neutral; the caller transmutes to the concrete `extern "system" fn` type — a generic transmute isn't provable, and `SameSizeAs` doesn't exist in this toolchain). **Property getters use the automation convention** — `HRESULT` return with the value in an out parameter — because cross-process calls go through the proxy stub generated from the type library. The Delphi TLB source (`function Get_Tx: RigParamX; safecall;`) is Delphi source sugar for that convention; assuming a direct return made the stub write through an out-parameter pointer that was never passed, which crashed in `RPCRT4.dll`. Slots: IRigX `Get_Status` = 12, `Get_Tx` = 32; `Release` = 2. GUIDs/`PM_*`/status codes from OmniRig's type library. **Activation caveat:** OmniRig is a 32-bit Delphi COM server (`LocalServer32`, registered via `/regserver`). Under WOW64, `HKLM\SOFTWARE\Classes\CLSID` is redirected, so its registration is visible only in the 32-bit registry view — a 64-bit process cannot resolve the CLSID (`REGDB_E_CLASSNOTREG` = `0x80040154`; the constant was previously miswritten as `0x800401F3`, which is `REGDB_E_READREGDB`). Activation uses `CLSCTX_LOCAL_SERVER` = `0x4`; it was miswritten as `2` (`CLSCTX_INPROC_HANDLER`), which produced `CLASSNOTREG` even on a correctly registered machine, because OmniRig's CLSID has only a `LocalServer32` key and no `InprocHandler32`. OmniRig never calls `RegisterActiveObject`, so `GetActiveObject` finds nothing either → the OmniRig method only works in a **32-bit build** of the app, which is why the release target is `i686-pc-windows-gnu` (a 32-bit client resolves the redirected CLSID view and attaches to the running OmniRig through Delphi's `CoRegisterClassObject` class table, or starts it; that is how N1MM+ and the other OmniRig clients work — N1MM+ is 32-bit). The connect error message probes the CLSID in both registry views (`RegOpenKeyExA` with `KEY_WOW64_32KEY`/`KEY_WOW64_64KEY`) so it distinguishes "not installed" from "installed but registered only in the 32-bit view", and the GUI note is bitness-aware via `cfg!(target_pointer_width)`. Field-confirmed on the user's machine: the CLSID is present in the 32-bit view (`LocalServer32` → `OmniRig.exe`) and absent from the 64-bit view and HKCU, while 32-bit PowerShell activates it fine (`Rig1.Status` = 4 online). The rig link status is refreshed into the message line every 20 polls (2 s), so a loose cable shows as "not responding" while the COM link is still alive; a failed COM call is treated as a dead connection (reconnect). Non-Windows: stub whose `connect()` errors
- **COM port** (`src/radio.rs` + `src/ptt.rs`): direct CAT polling with a per-model status command; 58 models, extracted from OmniRig's per-model rig INIs (field-tested against real radios) + vendor CAT manuals. Each probe = command bytes + read spec (`Until(term, cap)` terminator-inclusive, or `Count(n)` for fixed blocks) + timeout + TX rule(s): an OR of ANDs of byte tests `(data[i] & mask) == expect`, plus for the 1-byte Yaesu replies a `last_data` test (the byte before the trailing terminator, else the last byte — the prefix length varies). `parse` → `Some(0)` RX / `Some(1)` TX / `None` unusable (missing terminator for an indexed read, too short, no evaluable rule — a rule whose index lands on the terminator means a truncated command echo). Models: Icom CI-V `FE FE <addr> E0 1C 00 FD`, 15-byte reply, bit 0 of byte 13 (Xiegu G90 same protocol addr 0x88; X-6200 an 8-byte reply, byte 6); Kenwood/Elecraft K-series/Flex PowerSDR ASCII `IF;`, char 28 == '1' (SmartSDR `ZZIF;`, char 30 — the radio echoes its `ZZ` address); Yaesu FT-817/857/897 `…F7` 1-byte status, TX while bit 7 is **clear**, FT-847 `…E7` bit 7 **set** (polarity inverts between generations), FT-840/900 5-byte `FA` blocks with dual-VFO rules, FT-920/1000MP/100D and FT-990/1000 5–8 byte `FA` blocks, FT-767GX exactly 86 bytes **without** terminator (byte 85 bit 0, 400 ms timeout), FT-891/991/FTX-1 ASCII `TX;` (char 2: `2` = radio TX, `1` = CAT-keyed — **both** count as TX, the denoiser must bypass whenever the radio is or is about to be keyed; the FT-900 is CI-V, not ASCII). Skipped: FT-747 series (344-byte replies too slow at poll rate), Elad (niche)
- **Serial poll loop** (why it isn't a plain blocking read): the `serialport` crate reports a *timed-out* read as an error (and on Windows its `COMMTIMEOUTS` — `ReadIntervalTimeout = u32::MAX`, `ReadTotalTimeoutMultiplier = u32::MAX` — do not bound a no-response wait at all: the total timeout is `multiplier × buffer + constant` ≈ days), so a radio that answers without a terminator (the 1-byte Yaesu status) would never parse, and a dead radio would wedge the poller. Instead each poll is: `clear(Input)` (drops stale trailing bytes) → `write_all(cmd)` → deadline-bounded loop of `bytes_to_read()` + `read` (only read while data is actually queued; `set_timeout` is the backstop; 5 ms pace when idle) → `parse`. Any poll error is *transient* (the port may stay open); 5 consecutive failures close and reopen the port fresh. OmniRig holds the port exclusively while its method is selected (GUI note)
- The audio side is unchanged: state published as `Arc<AtomicU8>`; the capture callback forces the NR blend to 0 while keyed (1–3), `DISCONNECTED` falls back to the GUI slider; `process_frame` keeps running while keyed so the RNN stays warm; NR2's `resetTransient()` on the TX→RX edge
- GUI: "PTT method" dropdown + conditional fields (host/port for rigctld, default `localhost:4532`; rig slot dropdown Rig 1/Rig 2 + explanatory note for OmniRig; port name + baud 4800–115200 + 58-model dropdown for COM port), Connect/Disconnect, a colored RX/TX indicator, and the poller's status line
- Persistence: new keys `ptt_method` (0/1/2), `omnirig_rig` (1/2), `serial_port`, `serial_baud`, `serial_radio`; the historical `rig_connected` key name is kept (struct field is now `ptt_connected`) so old configs load, with defaults filling the new keys. Saved on every Connect/Disconnect/parameter change, restored at startup, which auto-reconnects to the saved source if the app was connected when it last exited
- v1 is poll-only (state in); keying the rig from the GUI (`T 0/1`) is a likely follow-up

## Real-time audio gotchas
- DSP runs inside cpal's audio callbacks (real-time threads): no allocations, no locks/mutexes, no file/network I/O, no `println!` — any of these cause glitches
- Device enumeration/selection happens on the GUI thread (startup, or on Refresh), never inside the callback
- The dropdowns are **filtered by direction**: the Input list contains only endpoints openable as input, the Output list only as output, each annotated with direction + rate (e.g. `Headset (in+out, 48 kHz)`) — an output-only speaker can never be picked as input (the all-endpoints list plus a silent fallback to index 0, where WASAPI lists speakers first, was the source of "Device does not support input" errors). Selections survive Refresh by name; the fallback when a name is gone is index 0 of the list, which is openable in that direction by construction (an empty list is an actionable error from `start()`)
- Capture and render callbacks run on separate threads and communicate only via the lock-free SPSC ring (`src/spsc.rs`) and `Arc<AtomicU32>` peak meters
- The GUI thread talks to the audio callbacks only through atomics: `Arc<AtomicU32>` peak meters in, the NR-amount and output-volume `f32`-bits, the filter-engine `Arc<AtomicU8>` and the rig PTT state out; the capture callback reads them with `Relaxed` loads once per callback, and the render callback reads the output volume once per callback (no mutexes in the callback)
- All DSP state (the DenoiseState, the NR2 engine with its ~0.9 MB gamma table, the biquads, frame accumulators, ring, resampler buffers) is allocated on the GUI thread at Start and moved into the stream closures; the one-time GUI-thread allocation is what keeps the RT path allocation-free
- Both streams use a small fixed shared-mode buffer (`BUFFER_FRAMES`, 960 frames ≈ 20 ms), not `BufferSize::Default`: the engine default can be far larger, and the render engine keeps its ring buffer full, so buffer depth is the heard echo latency (the callback period is always the engine's own, 10 ms at 48 kHz, regardless)

## Conventions
- Conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`)
- Commit and push only when the user explicitly asks — the user verifies sound on their own Windows machine (radio + PTT source) between builds; a successful build is not an approval
- Run `cargo test` before committing
- GitHub releases: tag scheme `v<major>.<minor>` (e.g. `v1.0`, `v2.0` — not `v2`), and **always** attach the precompiled Windows exe (`target/i686-pc-windows-gnu/release/ssb-noise-filter.exe`, the 32-bit release build) as a release asset
- CI on PR once a workflow is added
